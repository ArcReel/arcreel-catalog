# 模型巡检

你让目录跟上厂商：收录新模型，写入关停日期、后继和上线日期，修正价格，清理过期的人工数据。产出是一个数据 PR，同一时间只有一个，`Check catalog` 通过后合并，构建随即发布。需要新代码才能调用的模型、需要人裁决的事项，在 ArcReel 仓库开 issue，其余部分照常推进。巡检通常无人值守运行。

数据格式与构建规则以本仓库 README「构建」一节为准，开工前通读。条目字段以 ArcReel 仓库 `packages/arcreel-catalog-core` 的校验器为准。下文的「ArcReel 仓库」指它的本地克隆：云端会话中是另一个源仓库，通常与本仓库同级；找不到时，把 `https://github.com/ArcReel/ArcReel` 浅克隆到临时目录。

## 硬规则

1. **每项改动都有官方来源**，包括后继、日期和价格。官方来源指模型厂商或内置供应商渠道自己发布的文档、公告、定价页和更新日志。LiteLLM、models.dev、basellm、新闻和中转站只算信号。找不到官方来源就不改，记进运行记录。
2. **需要新代码才能调用的模型不进清单。** 判断方法见「新模型」。这类模型可以只收条目，供其他条目作后继，同时在 ArcReel 开 issue。
3. **只读公开页面。** 不使用维护者密钥，不调用厂商的列模型接口，也不调用方舟控制面的签名接口。
4. **公开仓库。** PR、issue 和评论只写技术事实与官方链接，不写客户、商业决策、定价策略、渠道关系或私有实现细节。

## GitHub 访问

所有 GitHub 操作都用 `gh api` 调 REST，在云端和本地都可用；云端的 GraphQL 会返回 403，`gh pr`、`gh issue` 子命令因此不可用。下文的 `{catalog}` 指 `repos/ArcReel/arcreel-catalog`，`{arcreel}` 指 `repos/ArcReel/ArcReel`。

## 1. 开工

1. fetch `origin`，找出 head 分支以 `model-sweep/` 开头的 open PR：`gh api '{catalog}/pulls?state=open&per_page=100' --jq '.[] | select(.head.ref | startswith("model-sweep/")) | .number'`。
2. **有这样的 PR 时接手它**，本次改动都追加在它的 head 分支上，不另开 PR。
   1. 读 PR 正文与评论：正文里的逐项表和运行记录，是之前各次运行的累积结果。审查意见（如 CodeRabbit）先到官方来源核实：成立就改，不成立就附官方链接回复，不因审查意见本身改数据。
   2. rebase 到最新 `origin/main`。冲突按改动意图解决，解决后重新核实受影响的那几项。
   3. 正文里记过的未决事项（例如上次 `Check catalog` 失败的原因）先处理。
3. **没有时**，从 `origin/main` 创建 `model-sweep/<YYYY-MM-DD>` 分支，日期取 UTC 当天。
4. 读上一个已合并巡检 PR 的正文，取 `{catalog}/pulls?state=closed&per_page=30` 中 head 分支前缀相同、`merged_at` 最新的那个。
   - 运行记录里留给后续巡检的待办，是本次的输入：例如未来的渠道下架日、只给了下限的关停日期、定时调价。日子已到的，本次处理。
   - 那次（以及接手 PR 的运行记录里）裁定「不改」的项，信号与官方页面都没有变化时沿用结论，不必重查。
5. 查已有 issue，避免重复开：ArcReel 中 open 的 `needs-triage` issue，以及标题或正文提到 `arcreel-catalog` 的 open issue；本仓库的 open issue。已关闭的巡检 issue 里有裁决的，按裁决处理。

## 2. 收集信号

1. 运行 `uv run python -m catalog_build signals`。它抓取 basellm、models.dev 和 LiteLLM，按类别列出信号，每类附说明；没有信号的类别也会列出，表示已检查。网络拿不到数据源时，把失败的地址记进运行记录，继续下一步。
2. 逐个读 [references/sources.md](references/sources.md) 中的官方页面，与 `data/` 对照：新模型、已宣布的弃用与关停、后继、价格变化、上线日期。页面打不开时，先试同一页面的其他形式（Markdown 版、`llms-full` 文本、英文站），都失败再记进运行记录。
3. 读第 1 步第 5 项找到的 issue 中，与目录数据有关的待办。

页面与信号多时，可以按供应商分给子 agent 核实，`data/` 由你统一修改。子 agent 逐项回报：对象、结论（改、不改或开 issue）、要写入的值、官方链接，以及支撑结论的原文摘录。

`build` 的警告不是信号，不必逐条处理；其中指向数据缺口的（例如因币种不符按未定价发布的模型），可以补人工条目。

本步完成的标准：每条信号、每个官方页面、每个相关待办，都在运行记录里有去向。去向是「已改」「不改，附理由」或「开 issue」三者之一。`missing-release-date`、`auto-successor` 这类数据缺口不影响模型能否调用，一次处理不完时，先处理内置供应商清单引用的条目，其余在运行记录里记为「留待下次」并写明数量。

## 3. 核实与修改

逐项到官方来源核实，再改 `data/`。拿不准时，按三点权衡：能否由官方来源核实；出错的后果，尤其是用户正在用的模型会不会被提前停用、默认模型会不会失效、费用估算会不会偏低；能否回退。实例会保留收到过的条目版本，所以已经发布的错误比还没写入的遗漏更难收回。

### 生命周期

- 关停日期只写官方给出的确切日期。「或更晚」「最早可能」一类的日期是下限，不写入，记进运行记录，下次再查。
- 厂商宣布弃用、但还没到关停日的模型，留在清单里，写上关停日期，不提前移除。
- 生命周期记在模型厂商层面，取仍在提供它的渠道里最晚的那天。渠道指模型厂商自营的 API 和本目录的内置供应商；Azure、Bedrock 这类转售方不算。内置供应商的官方页面在售就算仍在提供，不论本目录的清单是否列出它。所以写入或复核关停日期时，要查同一型号在其他内置供应商的在售情况。
- 只有某个渠道先行下架时，不改条目，在该内置供应商的清单里处理：加 `exclude`，或移除人工清单项。渠道下架日在未来时不提前处理，记进运行记录，下架日之后的第一次巡检再移出清单。
- 第三方数据源标为 `deprecated` 的文本模型，构建不会让它下线。查明关停日期后写进条目；查不到就保持可用。
- 写入生命周期时，退役模型如果原本来自自动构建，就把它的条目和清单项固化成人工数据，这样上游先删掉它，它仍能保留到期满。固化时字段取当前发布的值（`build` 写出的 `catalog.json`），模型别名只保留日期快照，中转站别名仍由构建生成。它的后继如果也是自动条目，一并固化。
- 写入的关停日期已满 90 天时，条目当场不再发布。上游没有同名模型的（媒体条目都是），同批按「到期清理」删除。
- 已关停但没有日期的模型，置真 `discontinued`，不编造日期。

### 拆分与名字归属

- 下线时间不同的型号，各自是一个条目，不能互为模型别名。
- 按下线时间拆分时，原条目 ID 留给模型厂商层面最晚关停的那个型号。这条只用于同一个通用名下的快照；新型号有自己的官方模型名时，用它自己的名字建条目。
- 判断一个名字归哪个条目，看人工数据认领名字的所有途径：主名和模型别名，按 README 的归一化规则比较。改名字归属前，先确认按通用名对应的用户模型会落到哪个条目。

### 后继

- 只写厂商官方指定的那一个。官方只说「迁移到某系列最新模型」时不写。
- 官方已指定后继、还没有关停日期的，只写后继，不写日期，也不置为下线。
- 后继必须是已存在、媒体类型相同的条目。目录里没有时，有完整官方资料就补条目，否则不写后继。
- 后继指向自动条目时，上游删掉它会让整份数据被校验器拒收。退役条目还在保留期内的，把后继固化成人工条目。

### 新模型

- 收录前确认现有调用通道能原样调用：读 ArcReel 仓库里该供应商的后端（`lib/backends/`）、内置调用端点（`lib/custom_provider/builtin_endpoints/`）和 `docs/api-docs/providers/<供应商>.md`。请求路径、参数形态、响应形态都与已收录的同类模型一致，后端里按型号名分支的逻辑（例如按名字匹配参考图上限）也能覆盖新名字，才算能调用。内置供应商渠道对这类模型有调用限制（例如有未决 issue 记录的限制）时，也不加进它的清单。
- 能力与价格字段取官方文档。校验器要求、官方却没给出的字段，不编造：这个模型先不收录，记进运行记录。
- 需要新代码的模型，在 ArcReel 开 `needs-triage` issue：写明模型、厂商文档链接、与现有调用端点的差异和建议。已有同类 issue 时，有新信息才补一条评论，不重复开。

### 价格与上线日期

- 价格取官方定价页，币种跟厂商主站一致（见 `data/upstream.json`）。LiteLLM 的差异只是信号，官方页面与目录一致时不改。
- 官方的分档计价，价目表的计量项与维度表达不了时，条目保持现状。会让费用估算明显偏低的，开 `needs-triage` issue。
- 官方宣布的定时调价，生效前不改，在运行记录里记为待办并写明生效日期，生效后的第一次巡检更新。
- 上线日期取官方发布说明或模型页写明的日期，只到月份的不写。型号名里的日期后缀是快照版本号，官方没有说明时不当作上线日期。两个官方页面给出不同的日子时不写，记进运行记录。

### 默认模型与清单

- 默认模型不能带关停日期（校验器会拒绝）。默认模型宣布退役时，改为该供应商清单里已收录、能调用的官方后继；没有这样的后继，就删除这个默认值。这两种改法由本条授权，不按「需要人裁决的事项」处理。
- 新收录的模型同时加进对应内置供应商的人工清单。默认模型留在人工清单里。

### 到期清理

- 过了保留期的人工条目，只有上游已不再包含它的名字时才删除（信号 `expired-cleanup`），引用它的人工清单项一并删除。上游仍保留同名模型时，条目留在 `data/`，构建靠它拦住上游；构建本来就不再发布它。

### 需要人裁决的事项

同一事实在两个官方页面上说法不同（上线日期除外，见上文），或改动符合 ArcReel 仓库 `docs/agents/escalation.md` 中「做错代价高」的判据时，不改这一项，在 ArcReel 开 `needs-triage` issue，写明事实、选项和推荐，PR 其余部分照常推进。在 ArcReel 发现的其他缺陷（例如内置调用端点推荐的模型已下线），按 escalation.md「范围外的真缺陷」处理。

## 4. 验证

1. `uv run python -m pytest -q`，再运行 `uv run python -m catalog_build build --check-only`，直到通过。后者要联网抓取上游；网络不通时记下原因，以 PR 上的 `Check catalog` 为准。
2. 重跑 `signals`：本次处理过的信号应当消失，或者在运行记录里写明为何保留。
3. 核对 diff：`git diff --stat origin/main...HEAD` 只含 `data/`，以及本次更新的 `references/sources.md`，不含 `catalog.json`、`manifest.json`。每个改动的条目和清单项，都能在逐项表里找到对应的行和官方链接。

## 5. 产出 PR

本次和接手的 PR 都没有数据改动时，不建 PR，把运行记录写进最终报告后结束。

1. 提交，信息为 `chore(data): <YYYY-MM-DD> 模型巡检`，日期与分支名一致。push 分支。
2. 新建 PR（`gh api -X POST {catalog}/pulls`），或更新接手 PR 的正文（`gh api -X PATCH {catalog}/pulls/<PR 号>`），标题同提交信息。正文包括：
   - **逐项表**：模型、情况、写入、官方来源，一项一行，来源是可点开的链接。接手时保留之前的行，追加本次的行。
   - **运行记录**：每次运行一小节，标明日期。列出没有改动的信号与页面及理由、打不开的页面、本次开出或引用的 issue；没有遇到需要新端点的模型时，写明已检查。
3. 合并：先试 `gh pr merge <PR 号> --auto --squash`，这是唯一走 GraphQL 的命令；检查已通过时它会直接合并。云端开不了 auto-merge 时，用 `gh api '{catalog}/commits/<head SHA>/check-runs'` 等 `Check catalog` 完成，成功后用 `gh api -X PUT {catalog}/pulls/<PR 号>/merge -f merge_method=squash` 合并。管理员身份可以绕过必需检查，所以只在 `Check catalog` 成功后合并。最后用 `gh api {catalog}/pulls/<PR 号> --jq .merged` 确认已合并，或确认 `auto_merge` 已开启。
4. `Check catalog` 失败时读日志：是本次数据的问题就修复或撤下那一项，重新 push；修不好时 PR 保持 open，在运行记录里写明原因，下一次巡检接手。

## 失败与停止

- `gh` 认证或 API 访问失败、push 被拒：停止，不建 PR，报告停在哪一步。
- 只完成了部分页面：照常提交已核实的改动，没读完的页面记进运行记录，下一次巡检补上。
- 结束时给出一两句结论：PR 链接与状态，或者停在哪一步、为什么。

## 维护本 skill

官方页面地址变了，或找到更合适的官方页面时，在同一个 PR 里更新 [references/sources.md](references/sources.md)，并在运行记录中说明。
